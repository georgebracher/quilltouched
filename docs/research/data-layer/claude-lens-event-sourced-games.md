# Event Sourcing in Games — Prior Art, Pitfalls, and a Replay-Versioning Policy for Everquill

Lens: event sourcing in games. Verdict up front: the event-sourced canon decision is sound and well-precedented, **provided one invariant is written down and enforced from day one** — Everquill must be *event sourcing* (fold over recorded outcomes), never *command sourcing* (re-execution of inputs through the engine). Every famous "replay broke" story in games comes from the second pattern. This distinction is the whole ballgame for the schema-evolution risk flagged in the brief.

---

## 1. Prior art map

### 1.1 The re-simulation branch (cautionary — this is what breaks)

RTS lockstep, Factorio, SC2, and roguelike seeds all store **inputs + seed** and re-run the engine deterministically. This is exquisitely version-fragile:

- **Factorio** stores only the map exchange string, mod list, and player inputs; a replay is a full re-simulation. The devs explicitly **disable replays the moment any prototype data changes** — a recipe tweak or crafting-speed change invalidates every prior replay. Save/load must be bit-deterministic and they treat any divergence as a bug, but *cross-version* replay is simply declared unsupported ([Factorio replay system](https://wiki.factorio.com/Replay_system), [Rseding91's deterministic save/load notes](https://gist.github.com/Rseding91/a309cf0a30782a2e96ef081c39326f42), [player complaints](https://steamcommunity.com/app/427520/discussions/0/3078754982925905812/)).
- **StarCraft II** solved cross-version replay by *shipping the old engine*: the client relaunches an older patch binary to play old replays — and even that broke at the Patch 3.0 file-format change, orphaning earlier replays ([Kotaku on Patch 3.0](https://kotaku.com/starcraft-iis-new-patch-wont-support-old-replays-1734891305), [Blizzard forums](https://us.forums.blizzard.com/en/blizzard/t/starcraft-2-old-replays-compatibility/41074)). "Keep every historical engine build runnable forever" is the only fix for re-simulation, and it is miserable.
- **Lockstep RTS generally**: determinism demands identical RNG streams, no platform float divergence, periodic state-hash desync detection — and desync recovery is famously hard ([lockstep overview](https://www.socratopia.app/library/math-for-game-devs-en/chapter-30), [gamedev.net desync thread](https://gamedev.net/forums/topic/685257-lockstep-desyncing-because-of-rng-i-think/5326905/), [yal.cc determinism prep](https://yal.cc/preparing-your-game-for-deterministic-netcode/)).
- **Roguelike seeds** (Slay the Spire et al.): a seed is a compressed command log; any patch that touches card pools, relic weights, or encounter tables silently changes what the seed produces — seeds are only "verified for the current patch" ([StS seed patch notes](https://steamcommunity.com/games/646570/announcements/detail/1667896308899681894), [seed compatibility](https://slaythespire-2.com/seeds)).

**Lesson for Everquill:** the engine WILL change (balance, plausibility tiers, new mechanics). If rebuilding a character sheet ever re-runs current engine logic against old events, old canon silently mutates — the event-sourced equivalent of a Factorio replay desync, except it corrupts live player state instead of a replay file. Everquill's design already leans the right way (seeded 2d6 *recorded* in the log), but this must be a hard rule: **the roll values, modifiers, tier, and applied deltas are stored in the event; replay never re-rolls and never re-derives.**

### 1.2 The recorded-facts branch (what works)

- **SpacetimeDB / BitCraft** — the closest living relative. An actual shipping MMO whose entire backend (chat, items, terrain, positions) runs as one module inside a database: all state in memory, durability via an **append-only write-ahead Commitlog**, mutations only through **atomic, deterministic reducers**, clients subscribe to table projections ([SpacetimeDB repo](https://github.com/clockworklabs/spacetimedb), [FAQ](https://spacetimedb.com/docs/intro/faq/), [Clockwork Labs on BitCraft](https://clockwork-labs.medium.com/spacetimedb-and-bitcraft-bc957a7faf40)). Validates Everquill's shape exactly: authoritative deterministic engine, append-only log as truth, everything readable is a projection. Note they run this for *thousands* of concurrent players; Everquill's tens-of-players alpha is three orders of magnitude below any scale cliff.
- **Elite Dangerous Player Journal** — the best in-the-wild example of a long-lived, schema-evolving, append-only JSON game event log: one JSON object per line with `timestamp` + `"event":"name"` + weak-schema key/value pairs, a header record carrying game version and file part, and a documented manual now at v32+ that an entire third-party ecosystem (EDDN, trade tools) consumes across years of schema drift ([Journal manual PDF](https://hosting.zaonce.net/community/journal/v32/Journal_Manual-v32.pdf), [journal docs](https://elite-journal.readthedocs.io/), [EDDN](https://github.com/EDCD/EDDN)). Proof that additive weak-schema JSON events survive years of game evolution if consumers ignore unknown fields and producers never repurpose existing ones.
- **EVE Online** — not globally event-sourced (single-shard SQL, 150M+ transactions/day), but its *economy legibility* comes from ledger-style append logs: wallet journals and market transaction records that players and CCP's economists audit ([single-shard architecture](https://www.gamedeveloper.com/game-platforms/feature-ccp-outlines-single-shard-mmo-development), [DB history](https://www.eveonline.com/news/view/a-history-of-eve-database-server-hardware), [30k users one shard](https://www.datacenterknowledge.com/servers/eve-online-30-000-users-on-one-server-shard)). Lesson: the ledger pattern is what makes a game world *auditable and trustworthy*; Everquill applying it to deaths and dice is the same move applied to narrative stakes instead of ISK.
- **Minecraft DataFixerUpper** — the canonical games answer to persisted-data schema evolution: versioned schemas plus composable DataFix rewrite rules, letting 2011 worlds load in current versions ([DFU repo](https://github.com/Mojang/DataFixerUpper), [minecraft.wiki](https://minecraft.wiki/w/DataFixerUpper), [community docs](https://github.com/kvverti/Documented-DataFixerUpper)). Also the cautionary half: DFU's generality is so expensive that building fixers consumed the large majority of game startup and spawned optimization mods ([cadmium](https://github.com/jellysquid3/cadmium-fabric), [LazyDFU](https://modrinth.com/project/hvFnDODi)). Lesson: upcasting chains absolutely work over 10+ years of schema churn, but keep the machinery simple and data-shaped — do not build a type-theoretic migration framework for a Postgres JSONB column.
- **Enterprise ES canon** — Greg Young's *Versioning in an Event Sourced System* ([Leanpub, free to read](https://leanpub.com/esversioning/read), [TL;DR](http://blog.approache.com/2019/02/versioning-in-event-sourced-system-tldr_10.html)) and the empirical study of 25 production event-sourced systems ([arXiv 2104.01146](https://arxiv.org/abs/2104.01146)) converge on five evolution tactics: **versioned event types, weak schema, upcasting, in-place transformation, copy-and-transform** — with weak schema + upcasting as the workhorses and in-place rewriting as the one everyone regrets. Marten's docs show the practical upcasting API shape ([Marten events versioning](https://martendb.io/events/versioning.html), [event-driven.io patterns](https://event-driven.io/en/simple_events_versioning_patterns/)).

### 1.3 Patterns that fit a solo-player, server-authoritative RPG specifically

At Everquill's volume (heavy player ≈ low hundreds of events/day; alpha ≈ tens of players → well under ~1M events/year; 10k players ≈ low hundreds of millions/year, still fine in Postgres), the entire distributed-ES problem space evaporates:

1. **One Postgres table, single writer, global sequence.** `(world_seq bigserial, event_id, character_id/subject, region_id, type, type_version, occurred_at_world, recorded_at, engine_version, ruleset_version, rng jsonb, payload jsonb)`. No Kafka, no EventStoreDB. Per-character and per-region "streams" are just indexed queries — which is exactly what the claim store and lazy rumor propagation need.
2. **Synchronous projections in the same transaction.** Append event + update current-stats/known-sheet/claim projections in one Postgres transaction. This deletes the entire "eventual consistency" pitfall class that dominates production ES war stories ([backend trade-offs](https://thebackenddevelopers.substack.com/p/event-sourcing-in-backend-systems-3e7), [Azure pattern doc](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)). It's a luxury only available at this scale — take it, and revisit only if 10k players actually arrives.
3. **Events as decision records with provenance.** Each event carries: inputs considered, RNG stream id + counter + raw rolls, modifiers, ruleset version, and the resulting state *deltas*. This satisfies auditable-dice, savescum-proofing, and replay-safety simultaneously.
4. **Idempotent append.** Mobile clients retry; the turn pipeline and world-clock worker will double-fire eventually. Unique constraint on a client/job-supplied `command_id`. A real production system grew a 100k-event stream purely from a non-idempotent background job ([planetgeek long-streams post](https://www.planetgeek.ch/2026/05/05/event-sourcing-you-better-prevent-long-event-streams/)) — Everquill's world-clock due-jobs worker is precisely that shape of risk.
5. **Rebuild-by-nuke is affordable.** At low millions of rows, rebuilding every projection from genesis takes minutes. Design projectors as pure folds so this stays true; snapshots are an optimization to defer, not a launch requirement ([Kafka/ES snapshot guidance](https://www.conduktor.io/glossary/event-sourcing-patterns-with-kafka)).
6. **LLM firewall.** Only engine-validated events append. The narrator and intent parser never write canon — Everquill already commits to this; it is also what makes the log trustworthy as a source of truth (the SpacetimeDB reducer discipline, applied to an LLM).

## 2. The five worst pitfalls (ranked) and mitigations

**P1 — Accidental command sourcing (replay re-executes engine logic).**
The moment a fold calls into live rules code ("recompute damage from the roll," "re-check plausibility tier"), every balance patch retroactively rewrites history — sealed deaths included. This is Factorio's replay invalidation transplanted into your canonical store.
*Mitigation:* events store resolved outcomes and applied deltas; folds only apply deltas. CI gate: a **golden-corpus replay test** — frozen fixture events from every schema version ever shipped, folded on every commit; projection diffs fail the build.

**P2 — Semantic drift disguised as compatible schema.**
The empirical study found the nastiest changes aren't structural but semantic: same field name, changed meaning (e.g., `damage` becomes post-mitigation instead of pre-mitigation) ([arXiv 2104.01146](https://arxiv.org/abs/2104.01146)). Weak-schema JSON hides this completely until projections are subtly wrong everywhere.
*Mitigation:* rule — **meaning change ⇒ new event type or new field name, never a reinterpretation.** Version bumps are for structure; semantics get new names. Document each event type's field semantics in a registry file that reviewers diff.

**P3 — In-place log rewriting / migration scripts touching the event table.**
The tactic every production team regrets ([Greg Young](https://leanpub.com/esversioning/read); [Doomen's production war stories](https://www.linkedin.com/pulse/ugly-event-sourcing-real-world-production-issues-dennis-doomen)). One botched migration and "sealed, auditable canon" is gone; you also break corroboration links and inheritance references pointing at event ids.
*Mitigation:* the event table is INSERT-only at the DB-privilege level (revoke UPDATE/DELETE from the app role). Corrections are **compensating events** (`RulingReversed`, `CanonErratum`) — which even fits the fiction. Transformation happens only at read time (upcasters) or, in extremis, via the snapshot-barrier escape hatch below.

**P4 — Projection/fold code changes without versioning (the "rebuild melted us" class).**
Changing claim-confidence math or known-sheet folding logic, then rebuilding in place, corrupts live read models and can't be rolled back ([Doomen on projection schema changes](https://www.linkedin.com/pulse/ugly-event-sourcing-projection-schema-changes-dennis-doomen)).
*Mitigation:* every projector carries a `projector_version`; changed logic rebuilds into **shadow tables**, diff/spot-check, then atomic swap. Cheap at this volume; keeps the "rebuildable projections" promise honest. The region-epoch rumor cache already has the right shape — apply the same epoch/version discipline to all projections.

**P5 — Unbounded or noisy streams from the world clock.**
Timer-driven systems (training blocks, pressure fronts, exam schedules) love emitting heartbeat/no-op events; the claim store can similarly bloat with re-observations that change nothing. Long streams are the top self-inflicted ES wound ([planetgeek](https://www.planetgeek.ch/2026/05/05/event-sourcing-you-better-prevent-long-event-streams/), [redpanda guide](https://www.redpanda.com/guides/event-stream-processing-event-sourcing-database)).
*Mitigation:* world-clock jobs emit events **only on state change**; re-observations that merely raise confidence update the claim projection's corroboration links but reference the original event rather than minting a near-duplicate. Budget alarm: alert if any character/region exceeds N events/day.

*(Honorable mention: player-authored free text inside events vs. GDPR/right-to-erasure. Standard fix is crypto-shredding — encrypt player-text payload fields per player, delete the key on erasure, canon structure survives. Cheap to add on day one, painful to retrofit.)*

## 3. Concrete replay-versioning policy (recommendation)

**Envelope (every event):**
`event_id (ULID) · world_seq · subject/character_id · region_id · type (string) · type_version (smallint, starts 1) · occurred_at_world · recorded_at · engine_version (git tag) · ruleset_version · command_id (idempotency) · rng {stream_id, counter, rolls[]} · payload (JSONB, deltas + provenance)`

**The policy, as enforceable rules:**

1. **Facts, not commands.** Events record decided outcomes (rolls, modifiers, tier, deltas). Replay = pure fold. Engine code may change freely because it is never on the replay path. `engine_version`/`ruleset_version` are *forensic metadata*, not replay inputs.
2. **Additive weak schema within a version.** New optional fields: allowed. Readers ignore unknown fields. Renaming, repurposing, or changing the meaning of an existing field: forbidden.
3. **Structural break ⇒ `type_version` bump + pure upcaster** `vN → vN+1`, applied lazily at fold time, chained for multi-step gaps (the Marten/Greg Young pattern). Upcasters are pure functions with no engine imports.
4. **Semantic break ⇒ new event type name.** Old type's fold logic (or a lossless upcaster into the new type) is kept forever. Never reinterpret.
5. **Golden corpus in CI.** Repo keeps frozen real sample events for every `(type, type_version)` ever shipped. CI folds the corpus and diffs projections on every commit. This is the cheap, automated substitute for Blizzard's "keep old binaries" and the single highest-leverage guard given the engine will churn during development.
6. **Snapshot barriers as the escape hatch, not the routine.** If an upcast chain for some type becomes untenable, the engine emits a `StateSnapshot` event per affected character/region as an epoch barrier; folds start from the latest barrier; pre-barrier events remain immutable for audit, journals, and legacy inheritance but leave the hot fold path. This is Young's "copy-and-transform" tamed into an append-only form. Expect to use it rarely — maybe at alpha→beta ruleset resets.
7. **Append-only at the privilege level; corrections are compensating events.** No exceptions, including dev convenience during alpha (alpha is exactly when the discipline is built or lost — wipe worlds instead of editing logs).
8. **Projector versioning + shadow rebuild + swap** for all read models (stats, known sheets, claim store, rumor caches, scene manifests).
9. **Synchronous same-transaction projections at current scale;** re-evaluate only at real 10k-player load. This eliminates the eventual-consistency pitfall class entirely.
10. **Do not build:** a DFU-style generic migration framework, per-event Avro/schema-registry infrastructure, or stream copy-migrations as routine practice. At Everquill's volume they are pure cost.

**Why this is the right trade:** Everquill's biggest stated risk — engine churn vs. old-event replayability — is mostly *dissolved* rather than solved: by storing outcomes (rule 1) the engine is free to change, and the residual risk shrinks to payload-shape churn, which weak schema + upcasters + a golden corpus (rules 2–5) handle with a few dozen lines of code, as proven at far larger scale by Elite's journal ecosystem and a decade of enterprise ES practice.
